# Оценка и объяснение

**f0.**
- Единственный движок — SwiftF0: `KARAOKE_F0_ENGINE=swiftf0` (по умолчанию). swift-f0 0.3.0, `SwiftF0(spin=False).detect(x, sr, fmin=65, fmax=1400) → PitchResult(timestamps, pitch_hz, confidence, loudness_db)`, хоп 16 мс, порог уверенности 0,5 в скоринге (`conf_min`).
- RMS-гейт −50 dBFS (`rms_gate_db`). Кадр озвучен при `conf ≥ 0,5`, `hz > 0` и `rms > гейта`.
- Если f0 бросил исключение: `ValueError` → 422 `bad_audio`, любое другое → 500. Запасного движка нет.
- Отложено, после хакатона: `torchcrepe full` на CUDA (hop 10 мс, periodicity < 0,1 → 0), high-pass 70 Гц, медианный фильтр на 5 кадров по центам, откат на `meta.frames` при падении f0.
- Всё сводится на сетку 10 мс.

**Задержка.**
- `r[k]` = 1 внутри нот, `v[k]` = 1 на озвученных кадрах, оба сигнала центрируются.
- `L* = argmax Σ(v[k+L]−v̄)(r[k]−r̄)` по `L ∈ [−100, 500]` мс с шагом 10, прямой корреляцией на каждом сдвиге.
- `L** = argmax H(L)` (доля попаданий по тону) в `L* ± 50` с шагом 10.
- `ρ` — нормированная корреляция в пике. Если `ρ < 0,2`, то `applied = hint`, иначе для `lag_source = calibrated` `applied = clip(L**, hint ± 120)`, а для остальных источников `applied = L**` ([[ADR-020 Калибровка в наушниках и источник задержки]]).
- `residual = L** − applied` уходит в ритм.
- Нет ни одного озвученного кадра (знаменатель корреляции 0): `estimated = hint`, без hint — 0; уточнение `L**` не делается, `confidence = 0`.

**Нота.** Окно `[t+30 мс, t+d−30 мс)` после `applied` (края по 30 мс обрезаются; если окно пустое — вся нота `[t, t+d)`), `m = 69 + 12·log2(f/440)`.
- `dc = ((100·(m−midi) + 600) mod 1200) − 600`, это питоновский `%`.
- Попадание: `|dc| ≤ tol_c`.
- `coverage` = озвученные кадры / все кадры ноты.
- `hit` = попавшие кадры / все кадры ноты. Для rap, rap_golden и free: `hit = coverage`.
- `cents` = медиана `dc` по озвученным кадрам, у нот без тона — `null`.
- `onset_ms`: первый из 3 подряд кадров с `|dc| ≤ tol+50`, ищем в `[t−0,15; t+min(0,4; 0,6d)]`.
- `stab_c` = std(dc − скользящее среднее 150 мс), без первых 80 мс.
- `perfect` = `hit ≥ 0,9` и `|onset| ≤ 80`.

**Агрегация.** `w = len·mult[type]`.
- `pitch = Σw·hit / Σw` по normal и golden.
- `rhythm = Σw·coverage·f(onset) / Σw`, где f = 1 при ≤80 мс и линейно падает до 0 к 300 мс.
- `extras = Σlen·perfect / Σlen`. Вибрато — stretch.
- `total = round(10000·(0,65·pitch + 0,25·rhythm + 0,10·extras))`.
- Строка = `100·(0,7·pitch + 0,3·rhythm)`. Грейды по scoring.json.
- `live_total` считается тем же ядром по `meta.frames`, логируется и возвращается в `result.score.live_total` (без `frames` — `null`).
- `octave_shift ∈ {−1, 0, +1}`: берутся кадры, попавшие по тону с точностью до октавы (`|dc| ≤ tol`); если их меньше 10 — 0, иначе медиана разницы в полутонах / 12, округлённая и обрезанная до ±1. Влияет только на `result.octave_shift` и подсказку `octave_info`, в очки не идёт.

**Подсказки.** По приоритету, не больше 3 общих и по 1 на строку:
1. `silence` (coverage строки < 0,2).
2. `golden_miss` (golden-нота с hit < 0,5).
3. `flat/sharp`: `|cents| > 0,6·tol` и ≥60% нот строки с одним знаком.
4. `late/early`: средний onset > 120 мс или `|residual| > 120`.
5. `unstable`: stab_c > 60 на нотах длиннее 0,4 с.
6. `octave_info`: без штрафа.
7. `praise`: строка ≥ `line_grades.Perfect` (90).
8. `latency_info` («скорректировали задержку на {applied} мс») — stretch, не реализовано.

Для `golden_miss` из слога убирается `~` (продолжение в UltraStar); если слог пустой, подсказка без него: «золотая нота в «…» мимо».

**Константы в Python.** Эти числа баланса зашиты в коде, а не в scoring.json; перенос в scoring.json — после демо, через ADR.
- `scoring/core.py`: `LINE_PITCH_W = 0,7`, `LINE_RHYTHM_W = 0,3` (балл строки), `PERFECT_HIT = 0,9`, `ONSET_WIN_MAX_S = 0,4`, `ONSET_WIN_FRAC = 0,6` (окно поиска onset), `ONSET_TOL_EXTRA_C = 50` (допуск onset сверх `tol`), а также `EDGE_TRIM_S = 0,03`, `ONSET_PRE_S = 0,15`, `STAB_SKIP_S = 0,08`, `STAB_WIN = 15`.
- `scoring/tips.py`: `SILENCE_COVERAGE = 0,2`, `GOLDEN_MISS_HIT = 0,5`, `FLAT_TOL_FRAC = 0,6`, `FLAT_SHARE = 0,6`, `TIMING_MS = 120`, `UNSTABLE_D_S = 0,4`, `UNSTABLE_C = 60`. Порог `praise` берётся из `line_grades.Perfect`.

scoring.json проверяется при старте бэкенда: есть все `tol_cents` (easy, normal, hard) и `mult` (normal, golden, free, rap, rap_golden), `lag_range_ms` возрастает, `onset_ok_ms < onset_zero_ms`, веса в сумме 1 ± 0,01, `grades` в `[0, max]`, `line_grades` в `[0, 100]`. Битый файл не даёт бэкенду стартовать.

**Тесты** (pytest, `backend/tests`, синтетика `app.scoring.synth` из demo.reference.json: 5 гармоник, чистый сигнал 16 кГц, всё в памяти):
1. Точное попадание: ≥9300, грейд S, все строки Perfect, |lag| ≤ 20.
2. +150 центов: normal <4000, easy ≥9000; +50 центов на hard ≥8500; подсказка sharp.
3. Задержка 250 мс без hint: estimated 250±20, итог ≥9000.
4. Отрицательный `wav_t0` (0,15 и 0,4 с записи до начала песни, задержка 100 мс): estimated 100±20, итог ≥9300.
5. Октава ±1: итог в пределах ±2%, `octave_shift = ±1`; две октавы вниз → −1; квинта вверх → 0 и без `octave_info`.
6. Тишина: ≤200, все `cents = null`, `estimated_ms` = hint или 0. Постоянный чужой тон 300 Гц: <3000. Свёртка: d(1150) = −50, d(−1150) = 50, d(1200) = 0.
7. Не спета golden-нота: её hit < 0,1, `pitch_pct` падает больше чем на 25.
8. Заглушённая строка: падает только она (≤10), другая Perfect.
9. rap/free: у free 0 очков, у rap `cents = null`, у rap-строки `pitch_pct = rhythm_pct`. Чарт: при пении на октаву ниже `sung` внутри нот в пределах 0,5 от цели.
10. Самопроверка каждого songs/* по guide (`refpipe check`).
11. Контракт-тест ключей: `contracts/fixtures/result.perfect.json` и `web/mock/result.*.json` имеют те же ключи, что ответ API; scoring.json из contracts загружается и проходит проверку.
12. После хакатона: golden-набор Сени (10–15 реальных дублей) в коридорах, опоздание в одной строке.
