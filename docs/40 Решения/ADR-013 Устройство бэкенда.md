# ADR-013 Устройство бэкенда

**Статус:** принято · **Дата:** 2026-10-08 · **Решили:** Паша

## Контекст
Бэкенд асинхронный (FastAPI), но оценка дубля — тяжёлая CPU-работа (f0 + скоринг). На защите и на площадке нужно за секунды понимать, что всё живо и какая версия крутится. Шаблон взят из курсовой практики по FastAPI.

## Решение
**Модули `backend/app/`:**
- `main.py` — создание приложения, lifespan: загрузка f0-модели один раз и прогрев на 1 с синтетического тона, открытие БД.
- `core/config.py` (pydantic-settings, всё из env, без хардкода), `core/logging.py` (JSON-логи), `core/version.py`.
- `api/health.py`, `api/songs.py`, `api/takes.py`, `api/leaderboard.py`, `api/challenges.py` — тонкие роутеры.
- `scoring/` — чистые синхронные функции score-v1, без I/O. `f0/` — движки за протоколом `F0Engine` (swiftf0, torchcrepe, frames-fallback).
- `store/` — SQLAlchemy async + aiosqlite, `create_all` на старте, без миграций.

**Служебные эндпоинты:**
- `GET /healthz` — без префикса `/api/v1`: это liveness для Docker/Caddy, а не часть версионируемого API. Ничего не трогает, отвечает мгновенно.
- `GET /api/v1/version` — `{"app": "0.3.1", "git_sha": "a2ad092", "scoring": "score-v1", "f0_engine": "swiftf0-0.3.0"}`. Версия приложения из одного источника: `project.version` через `importlib.metadata`, а `git_sha` — build-arg образа. Ловушка: версия не хардкодится в коде и обязана совпадать с тегом образа (CD это проверяет).
- `GET /api/v1/health` — end-to-end: для каждого компонента статус, версия и время ответа в мс: БД (`SELECT 1`), f0-модель (инференс 0,25 с тона), каталог `songs/` (чтение одного reference.json), CUDA-воркер пайплайна (ping, только если задан `PIPELINE_URL`). Итог `ok | degraded | down`, HTTP 200 или 503. Проверки идут параллельно через `asyncio.gather` с таймаутом 2 с на каждую.

**Не блокируем event loop:** f0 и скоринг — в `asyncio.to_thread` за `asyncio.Semaphore(2)`; загрузка WAV через `UploadFile.read()`; все проверки health асинхронные. Если упрёмся в GIL — `ProcessPoolExecutor`.

**Версионирование и CD:** релиз = git-тег `vX.Y.Z`, CD-джоб проверяет, что тег равен `project.version`, собирает образ и пушит в GHCR с тегами `X.Y.Z`, `X.Y`, `latest`, `sha-<short>`. Пуш в `main` → образ `edge` + `sha-<short>` для онлайн-стенда. Почему так: тег — осознанный релиз (`demo-1` = `v0.1.0`), а `main` — непрерывная сборка для проверки на VPS; PR образы не публикуют.

**Docker:** multi-stage (builder с uv → `python:3.12-slim`), `uv sync --locked --no-dev`, непривилегированный пользователь, `HEALTHCHECK` через `/healthz` (python urllib, без curl). compose: `api` + `caddy`, volumes `data/` и `songs/` (read-only), сеть, лимиты CPU/RAM, `logging: json-file` с ротацией.

**Логи:** JSON в stdout, `request_id` на каждый запрос. На каждый дубль одно событие `take_scored`: `song_id, difficulty, dur_s, lag_hint_ms, lag_est_ms, lag_applied_ms, rho, total, pitch_pct, rhythm_pct, f0_engine, f0_ms, score_ms`. Это и отладка на площадке, и данные для баланса с Сеней.

**pre-commit:** `ruff check --fix`, `ruff format`, `end-of-file-fixer`, `trailing-whitespace`, `check-added-large-files --maxkb=1024` (mp3 эталонов ≤1 МБ), `check-json`, `check-yaml`, `check-merge-conflict`, `detect-private-key`. Для GDScript — `gdformat`/`gdlint` из gdtoolkit (по желанию Макса).

**CI:** ruff check, ruff format --check, pytest с coverage (`--cov=app --cov-fail-under=80` после появления кода), валидация JSON-контрактов.

## Альтернативы
Litestar; синхронный бэкенд; Redis-очередь для оценки; Poetry вместо uv.

## Последствия
Все пути API под `/api/v1` (контракты обновлены). Перед защитой проверка одной командой: `curl localhost:8000/api/v1/health`.
