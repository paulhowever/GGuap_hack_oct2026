# ADR-019 Публичные данные и честность дуэлей: вызов только с ok-дубля, без публичного client_id, имена из профиля

**Статус:** принято · **Дата:** 2026-10-15 · **Решили:** Паша

## Контекст
Финальное ревью второго дня нашло три проблемы.
- **Нечестный дубль мог стать вызовом.** `POST /challenges` не смотрел на `integrity`. Подозрительный дубль (например, реплей фонограммы на 10000 очков) превращался в ссылку, и каждый соперник проигрывал владельцу, которого нельзя обогнать.
- **`client_id` был публичным.** Лидерборд отдавал его в каждой строке, `GET /takes/{id}` — в результате. Владение профилем сервер не проверяет ([[ADR-015 Вход по нику без пароля]]), поэтому любой, кто увидел чужой `client_id`, мог переписать ник и аватар игрока через `POST /players`.
- **Имена в дуэлях отставали от профиля.** Владелец и соперники в `GET /challenges/{id}` и `opponent` в блоке `challenge` брали имя, сохранённое в дубле, а лидерборд показывает ник из профиля. После переименования один игрок назывался по-разному.

## Решение
- **Вызов только с честного дубля.** Новый вызов создаётся, лишь если `integrity.status == ok`; иначе `POST /challenges` отвечает 422 `challenge_take_not_ok` (для `suspect`, `incomplete` и `unverified`). Уже существующий вызов для дубля возвращается как раньше: идемпотентность не меняется, проверка действует только там, где вызов был бы создан. 404 `take_not_found` без изменений.
- **`client_id` не публикуется.**
  - `GET /leaderboard/{song_id}`: в строках нет `client_id`. Необязательный параметр запроса `client_id` проверяется тем же регулярным выражением uuid, что и в `POST /players` (неверный — 422). Строка, принадлежащая этому игроку, получает `"me": true`, остальные, а при отсутствии параметра все, — `"me": false`. Ранжирование, ник и аватар не меняются.
  - `GET /takes/{take_id}` отдаёт сохранённый результат с `"client_id": null` (ключ остаётся, значение обнулено). Ответ `POST /takes` сохраняет настоящий `client_id`: отправитель его и так знает. Это единственное намеренное отличие GET от POST, остальное тело совпадает.
  - `GET /challenges/{id}` не содержит `client_id` ни у владельца, ни у соперников.
- **Имена дуэлей из профиля.** Имя владельца и соперников в `GET /challenges/{id}` и `opponent` в блоке `challenge` ответа `POST /takes` — ник из профиля, если у дубля есть `client_id` с профилем, иначе `player` из дубля. То же правило, что в лидерборде. Блок `challenge` в сохранённом результате фиксируется в момент отправки дубля, `GET /takes/{id}` отдаёт его без пересчёта.

## Альтернативы
- **Доказательство владения профилем** (секрет при создании профиля или подпись `KARAOKE_SECRET`) закрыло бы подмену полностью, но возвращает [[ADR-015 Вход по нику без пароля]] к паролям по сути. Отложено как stretch; пока защита — непубличность `client_id`.
- **Показывать integrity владельца в вызове вместо запрета.** Подозрительный вызов остался бы в игре с пометкой. Отвергнуто: ссылку всё равно разошлют друзьям, проще не создавать вызов с нечестного дубля.

## Последствия
- Godot подсвечивает «я» в лидерборде по `me`, передавая свой `client_id` (из `voice.client_id()`) параметром запроса. Сравнивать `client_id` строк больше нечем и не нужно.
- Godot обрабатывает 422 `challenge_take_not_ok` на «Вызвать друга»: «этот дубль не в зачёте — спой честно, чтобы бросить вызов».
- Godot читает `GET /takes/{id}` без `client_id` (там `null`); свой `client_id` берёт из моста, а не из результата.
- Переименованный игрок виден в дуэлях под новым ником. В уже сохранённом результате чужого дубля `challenge.opponent` остаётся таким, каким был при отправке.
- Ранее созданные вызовы с нечестных дублей не отзываются: проверка работает при создании.
- Остаточный риск: `client_id` по-прежнему единственный ключ профиля, и кто его узнал другим путём (общий браузер, лог), может переписать профиль.
